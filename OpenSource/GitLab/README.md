# GitLab (Docker / Omnibus)

Self-hosted GitLab Community/Enterprise Edition, run as the official Omnibus
Docker image behind a host Nginx reverse proxy. Nginx terminates TLS; GitLab's
own bundled Nginx stays internal on plain HTTP.

## Layout

```
GitLab/
├── README.md
├── gitlab-nginx.conf          # Reverse proxy template (placeholders: gitlab.example.com, 127.0.0.1:8929)
└── scripts/
    ├── gitlab-docker-install.sh   # Generates docker-compose.yml, starts GitLab, wires up Nginx/certbot
    ├── gitlab-docker-backup.sh    # Runs gitlab-backup create + saves /etc/gitlab config
    └── gitlab-docker-restore.sh   # Restores a gitlab-backup archive into a running instance
```

Each installed instance lives at `/var/www/docker/gitlab/<domain>/`, containing:

| Path                          | Container path      | Contents                                  |
|--------------------------------|----------------------|--------------------------------------------|
| `docker-compose.yml`           | —                    | Generated by the install script            |
| `config/`                      | `/etc/gitlab`        | `gitlab.rb`, `gitlab-secrets.json`, SSH host keys |
| `logs/`                        | `/var/log/gitlab`    | Application & Nginx logs                   |
| `data/`                        | `/var/opt/gitlab`    | Repositories, uploads, DB, `backups/`      |

## Prerequisites

- Docker + Docker Compose plugin
- A public DNS record for the domain (GitLab must not be run on `localhost`)
- Nginx + certbot on the host if using the bundled reverse-proxy setup
- **A free host port for Git-over-SSH.** The host's own `sshd` almost always
  already owns port 22, so GitLab needs a different host port (default
  `2222`) mapped to the container's port 22.

## Install

```bash
./scripts/gitlab-docker-install.sh
```

You'll be prompted for:

- **Domain** (e.g. `gitlab.example.com`)
- **HTTP port** — host port GitLab's web UI binds to, `127.0.0.1`-only
  since Nginx proxies it (default `8929`)
- **SSH port** — host port for Git-over-SSH, bound publicly (default `2222`)
- **Edition** — Community (CE, default) or Enterprise (EE)
- **Image tag** — pin a version (e.g. `17.5.2-ce.0`) or use `latest`

The script then:

1. Creates `/var/www/docker/gitlab/<domain>/{config,logs,data}`
2. Writes `docker-compose.yml` with a `GITLAB_OMNIBUS_CONFIG` block setting
   `external_url`, `nginx['listen_port'] = 80`, `nginx['listen_https'] = false`,
   and `gitlab_rails['gitlab_shell_ssh_port']`
3. Pulls the image and starts the container (`docker compose up -d`)
4. Optionally tails logs while GitLab runs its first-boot `reconfigure`
   (can take several minutes)
5. Optionally requests a Let's Encrypt cert and installs the Nginx vhost from
   `gitlab-nginx.conf`
6. Optionally opens the SSH port in `ufw`
7. Optionally prints the initial `root` password from
   `/etc/gitlab/initial_root_password` (this file is deleted ~24h after first start)

## Configuration

GitLab reconfigures itself from `/etc/gitlab/gitlab.rb` on every container
start/restart. To change settings after install:

```bash
cd /var/www/docker/gitlab/<domain>
docker compose exec gitlab editor /etc/gitlab/gitlab.rb
docker compose restart
```

Anything set via `GITLAB_OMNIBUS_CONFIG` in `docker-compose.yml` is
re-applied on every start and takes precedence — edit that block instead if
you want changes to survive a `docker compose down && up`.

## Nginx Reverse Proxy

`gitlab-nginx.conf` proxies `443` to the HTTP port chosen at install time and
redirects `80` → `443`. It sets `client_max_body_size 0` (no limit — needed
for large repos/LFS/CI artifacts) and long proxy timeouts for big git
operations. The install script copies it to
`/etc/nginx/sites-available/<domain>` and substitutes the real domain/port.

## Backup

```bash
./scripts/gitlab-docker-backup.sh
```

Prompts for a backup directory (default `/home/backup`) and which installed
instance to back up, then:

1. Runs `gitlab-backup create` inside the container (full backup, or
   `SKIP=...` database-only for a fast pre-upgrade snapshot)
2. Copies the resulting `*_gitlab_backup.tar` out of `data/backups/`
3. Also tars up `config/` (`gitlab.rb`, `gitlab-secrets.json`, SSH host keys)

Both land in `<backup-dir>/gitlab-<domain>/<timestamp>/`.

> [!warning]
> `gitlab-backup create` does **not** include `/etc/gitlab`. Losing
> `gitlab-secrets.json` makes an existing application backup undecryptable
> (CI/CD variables, tokens, 2FA secrets) — that's why the config archive is
> saved alongside every backup.

## Restore

```bash
./scripts/gitlab-docker-restore.sh
```

Lets you pick a backup folder and timestamp, then a running instance to
restore into. It copies the archive into that instance's `data/backups/`,
stops `puma`/`sidekiq`, runs `gitlab-backup restore`, and restarts GitLab.
Requires typing `yes` to confirm — **this overwrites the target instance's
repositories, database, and uploads.**

If restoring into a fresh instance (not the one the backup came from), also
restore `gitlab-secrets.json` from the config archive as the script's output
instructs, or existing encrypted data won't be readable.

## Updating

```bash
cd /var/www/docker/gitlab/<domain>
# edit the image tag in docker-compose.yml, then:
docker compose pull
docker compose up -d
```

Take a database-only backup first (`gitlab-docker-backup.sh`, option 2) so
you can roll back if the upgrade fails.

## Useful Commands

```bash
docker compose up -d        # start
docker compose down         # stop
docker compose restart      # restart / reapply gitlab.rb changes
docker compose logs -f gitlab
docker compose exec gitlab gitlab-ctl status
docker compose exec gitlab gitlab-rake gitlab:check SANITIZE=true
```
